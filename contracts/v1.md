## Scope and architecture

Two scenarios only: `radlab_stale` and `sleep_vigilance`.
One demo crew member (`crew-demo-1`) and one detector pair (`DosTel1`, `DosTel2`).
Follow the named implementation plans: React + TypeScript + Vite, FastAPI and SQLite,
with bundled assets and loopback-only runtime access. The root README and CONTRIBUTING
still describe the earlier dependency-free browser app; Hamza and El Mahdi must align
those shared instructions with the approved kickoff. No dependency manifests are changed
by this contract handoff.

The research pipeline produces candidates for review; it is not the runtime evaluator.
Historical detector readings, synthetic crew observations and device measurements retain
their separate provenance. Prototype settings are not clinical cutoffs.

## Runtime requirements from the team plan

### Endpoints and time

| Request | Response and behavior |
|---|---|
| `POST /api/v1/runs` with `{"scenario_id":"radlab_stale"}` or `{"scenario_id":"sleep_vigilance"}` | `201` and `{"run_id":"…","scenario_id":"…","initial_as_of":"…","range_start":"…","range_end":"…"}`. The RadLab range is fixed from `2022-04-01T23:00:00Z` through `2022-04-02T01:04:59Z`. For the behavioral fixture, use `2026-01-10T09:00:00Z` as the initial time and range start, and `2026-01-10T10:00:00Z` as the range end. Baseline and sleep rows before the range are visible as history. |
| `GET /api/v1/runs/{run_id}/state?as_of=<UTC ISO timestamp>` | `200` and the state envelope below. Read-only, with an explicit `as_of`. Parse it as a timestamp and enforce the run range. Observations and incident transitions after `as_of` stay out of the response. |
| `POST /api/v1/runs/{run_id}/observations` | Behavioral scenario only. Accept `submission_id`, `observed_at`, and a batch of entries `[{metric,value,unit,source_id,metadata?}]`. The UI supplies the current mission clock for a new check-in. Server validates scope, units, source, timestamps and per-metric input shape, then adds IDs, subject and provenance. First insert `201`, identical retry `200` with the same IDs, different payload with the same submission ID `409`. The batch is atomic. |
| `GET /api/v1/runs/{run_id}/observations?as_of=<UTC ISO timestamp>&source_id=<optional>&metric=<optional>&limit=180` | `200` and `{"observations":[...]}`, in chronological order. Select the most recent matching observations up to the limit before ordering them for display. Use this for the chart/history. The state endpoint includes every observation referenced by the returned evidence, source statuses, or incident history, with each ID included once. |

Unknown run returns `404`. Invalid payload, metric, source, unit or time range returns `422` with a message the UI can display. Network errors get a retry state. On seek or reset, the UI discards a response for an older clock or run if it arrives late.

### State fields

- **Observation** — `id`, `subject_id` (null for cabin telemetry), `metric`, `value`, `unit`, `observed_at`, `source_id`, `provenance` and optional `source_timestamp` and `metadata`. Preserve input metadata needed for comparability and auditing. Provenance values are `REAL_HISTORICAL`, `SYNTHETIC` and `LIVE_MEASURED`. In the demo input form, numeric self-reports are labeled as sample entries and stored as synthetic. A reaction test actually performed on the laptop is `LIVE_MEASURED`.
- **Source status** — `source_id`, `metric`, `state`, `last_observation_id`, `age_seconds`, `reason_code`. States are `current`, `stale`, `missing`, `invalid` and `conflicting`. Last ID and age are null when there is no reading. A stale observation can be displayed with its age and historical label.
- **Evidence** — `code`, `observation_ids` and `detail`. Baseline comparisons add `baseline_id` and the baseline observation IDs. The engine provides the detail string for the demo. The UI renders supporting, conflicting and missing evidence from the assessment.
- **Assessment** — `id`, `rule_id`, `rule_version`, `state`, `title`, `supporting_evidence`, `conflicting_evidence`, `missing_inputs`, and `action_ids`. States are `observed`, `watch` and `insufficient_data`. An assessment may have no supporting evidence if inputs are missing. A complete comparison can report that the demo pattern did not trigger.
- **Action** — `id`, `label`, `required_resource_ids`, `available`, `unavailable_reason` (null when available). IDs point to an existing UI action or a read-only information panel. Resources are determined by scenario configuration. Keep unavailable actions visible with a reason and expose an available fallback.
- **Incident** — `id`, `source_id`, `state` (`open` or `resolved`), `opened_at`, `closed_at` (null while open), and `last_observation_id` for the observation that preceded the gap. Its stable ID is derived from source and preceding observation, within the run. The state envelope includes incidents known by `as_of`.

For scheduled inputs, `last_observation_id` and `age_seconds` refer to the latest observation eligible for the current assessment. A baseline or prior session can remain visible in history when the current session is missing.

## 4. Rules for the demo

| Rule | Deterministic behavior | What the evidence supports |
|---|---|---|
| `SOURCE_FRESHNESS@1` | For each configured source, find its latest eligible reading at or before `as_of`. At whole-second precision, current through age 300 s, stale from 301 s. Create one incident at +301 s and close it on the first subsequent reading. A source with no eligible reading is missing. Keep the last reading visible with its age. | The RadLab archive supplies measurement timing and the observed gap. The 300 s setting is a demo choice. Use it per source. It describes data freshness, and the gap’s cause is unknown. |
| `SLEEP_VIGILANCE@1` | At the scheduled morning assessment, use the three most recent scheduled overnight slots, one valid sleep value per slot. Require all three and a five-night seeded baseline. Short sleep means ≥60 min below baseline in at least two slots. Require a comparable reaction result from the current session and its five-test baseline. Slower means ≥20% above that baseline. If both conditions are true, return `watch` and **Sleep and vigilance change**. If required inputs or comparable baselines are missing, return `insufficient_data` and identify the inputs. Otherwise return `observed`. | Agent 2 linked the association to `EVID_SLEEP_003` and `EVID_COG_001`. The window, baseline count and cutoffs are explicit prototype settings. The result is a comparison with the demo baseline. It establishes neither a diagnosis nor the cause of the change. |

Behavioral fixture uses Jan 8–10 as the three sleep slots and Jan 10 morning as the reaction session. Seed a **clearly labeled sample result** of 310 ms available at `09:01:00Z`. This is 24% above the 250 ms fixture baseline and should trigger `watch`. The live browser task may produce any value. Preserve the sample result for a repeatable demo and give live results their own source metadata.

Record median response time from completed valid trials, with trial count, false starts and task version as metadata. Make a 30–60 second local reaction check with practice/instructions and a keyboard control. Compare only complete tests with the same task version and declared comparable input setup. An interrupted task creates no completed result. The fixture comparability profile is synthetic; a changed device/profile gets an observed result that stays in history with comparability unknown. The short task measures the demo’s response time. It has no clinical cutoff.

Keep fatigue optional and descriptive. Mood and stress stay in the check-in. A blank field remains missing. When the reaction task resource is disabled, show **Reaction check unavailable** and offer **Review available inputs**. Keep the assessment pending. Avoid presenting a sleep log or a self-report as a substitute for the missing reaction result.

## Confirmed evaluator boundary

Use the suggested plan signature with plain Python dictionaries/lists:

```python
from backend.engine import evaluate

state = evaluate(
    scenario_id,
    run_id,
    as_of,
    observations,
    resources,
    policy,
)
```

| Argument/result | Representation and responsibility |
|---|---|
| `scenario_id` | One of the two scenario strings above |
| `run_id` | Opaque, non-empty string; Hamza owns run creation/isolation |
| `as_of` | UTC ISO timestamp string at whole-second precision, ending in `Z` |
| `observations` | List of Observation dictionaries. Hamza supplies all run/scenario observations visible through `as_of`, including baseline and incident history inputs; do not apply the chart endpoint's 180-row limit |
| `resources` | Dictionary mapping resource IDs to booleans; e.g. `{"local_reaction_task": true}`. An absent resource is unavailable |
| `policy` | Parsed, versioned configuration dictionary owned by El Mahdi, stored in `rules/demo-v1.json`; Hamza loads it outside the evaluator |
| Return value | JSON-serializable State dictionary with `schema_version: 1`, `run_id`, `scenario_id`, `as_of`, `sources`, `observations`, `assessments`, `actions`, `incidents` |

The engine has no I/O, database access, wall-clock reads or randomness, does not mutate
inputs, and produces deterministic results. It also excludes future observations
defensively. Hamza owns request/input validation and maps invalid requests to the
HTTP errors above; evaluator/programming failures must not silently return preview data.

Expected sources, UTC scheduled slots, fixed baseline windows, task comparability,
rule versions and prototype thresholds live in [rules/demo-v1.json](../rules/demo-v1.json).
It contains `schema_version`, the default `resources` map and a `scenarios` map keyed by
scenario ID. Pass the full parsed policy to `evaluate`; pass a resource map separately
so the adapter can disable a task for B04. The evaluator never reads files and does not
fall back to policy resource defaults when a resource is absent from the explicit map.
No shared backend model or API implementation is introduced here.

Within a run, derive incident IDs using the example pattern
`stale-{source_id}-{preceding_observation_id}`; identify persisted incidents by
`(run_id, incident_id)`. Repeated evaluation and rewind cannot create new IDs or expose
future closures. A reading arriving at exactly the potential opening time takes
precedence and prevents that incident.

The state contains every referenced observation once, including references from source
statuses, evidence/baselines and incidents. Observation arrays in the example files are
kept in their original order; consumers must join by ID instead of array position.
Optional mood/stress remain in the check-in/history and never drive an assessment.

### D5 vocabulary

All existing example values remain unchanged. UI components render returned text
and state; they do not choose their own replacements.

- Reaction baseline ID: `crew-demo-reaction-v1`.
- Freshness title: join configured source name and returned state with ` · `,
  e.g. `DosTel1 current · DosTel2 current` or the exact Example A title.
- Behavioral `observed` title: **Demo pattern not observed**.
- Preserve **Sleep and vigilance change** for a triggered behavioral comparison and
  **Vigilance data missing** for the exact Example B case.
- Other incomplete behavioral comparisons: **Comparison incomplete**.
- Unavailable reaction action reason: **Reaction check unavailable**.
- Missing-input names: `sleep_duration`, `reaction_time`, `sleep_baseline`,
  `reaction_baseline`; an incomparable current reaction is unsatisfied
  `reaction_time`, with its reason explained separately.

| Source reason code | Meaning |
|---|---|
| `within_demo_window` | Latest valid detector reading is at most 300 seconds old |
| `older_than_demo_window` | Latest valid detector reading is at least 301 seconds old |
| `no_eligible_observation` | No visible reading exists for a configured detector |
| `scheduled_input_received` | Eligible input exists for the scheduled assessment |
| `current_session_missing` | No completed current-session reaction result exists |
| `scheduled_input_missing` | A required scheduled sleep input is absent |
| `invalid_observation` | The relevant visible input is invalid |
| `incomparable_reaction_result` | Current completed reaction result has a different task/profile |
| `conflicting_observations` | Relevant evidence explicitly disagrees; cause is unresolved |

The engine marks unusable finite readings/units/trial metadata invalid; a newer invalid
detector reading does not close an existing gap. Sleep selection uses the latest valid
value in each required UTC day. API adapters still validate required Observation fields,
scope, units and submission shape. Duplicate visible IDs, nonfinite JSON values and
invalid replay timestamps are rejected with `ValueError`, not replaced with invented data.

The plan reserves conflicting source/evidence states but does not define a conflict input
encoding or numeric disagreement threshold. This implementation emits an empty
`conflicting_evidence` list; it never infers a fault from differing detector values.
Any future conflict rule needs an explicit contract/policy change.

An incomparable completed reaction is still a `current` source reading, with reason
`incomparable_reaction_result`, while the assessment is `insufficient_data`. This keeps
measurement availability separate from suitability for the baseline comparison.
Incomplete tasks are not eligible completed results. A completed but invalid or
incomparable latest result cannot fall back to an older comparable sample.

Additional evidence codes used outside the unchanged examples are `invalid_observation`,
`sleep_comparison`, `sleep_inputs_incomplete`, `slower_reaction`, `reaction_comparison`,
`reaction_comparability_unknown` and `reaction_baseline_incomplete`. Evidence details
include the actual referenced observations and, where applicable, the baseline ID.
Freshness missing-input entries name the affected detector; behavioral entries use the
four metric/baseline names above. Optional self-reports remain unchanged in caller-owned
history/check-in data and do not enter either assessment.

### Example B completeness

Example B's response omits reaction baseline rows because its current reaction result
is missing. The full seeded input still includes those five rows. Exact Example B
reproduction should therefore use the full seed input, then include only observations
referenced by the returned state. An actual missing reaction baseline must still make a
comparison insufficient. Do not use the eight-row example response as the full
behavioral dataset.

A disabled reaction resource changes action availability; it does not manufacture a
missing observation or discard an already completed comparable result. B04 exercises
the missing-reaction state with that resource disabled. Both the missing-result and
complete-result variants are covered by engine tests.
